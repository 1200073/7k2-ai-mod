# 方法论 —— 怎么从二进制里反推出语义

> 本项目**没有符号表**、**没有调试信息**，全靠 Ghidra + 源码对照 + 实测验证。
> 下面是**真正有效的方法**和**浪费时间的方法**，按性价比排序。

---

## ⭐ 方法 1：浮点常量反查（命中率最高的那一招）

### 适用场景

你要找一个"体内用了某个特定数值"的函数。

### 为什么有效

**浮点常量在 PE 里是 `.rdata` 常量池 + 绝对地址引用** ⇒ 可以精确反查"谁引用了这个常量"。

**⇒ 比猜代码形状可靠得多，而且成本只有一次搜索。**

### 实例

要找 `NationBase::civilian_killed`（杀掉平民/叛军时的惩罚结算）。

**手里的线索**：源码里它同时用了 `-10.0f` 和 `-1.0f`：

```c
change_reputation( killedCount * -10.0f );   // 商队
change_reputation( killedCount *  -1.0f );   // 平民/叛军
```

**做法**：在 `.rdata` 里找这两个 float 常量，然后反查"哪个函数同时引用它们"。

**⇒ 全 exe 只有一个函数命中 ⇒ `0x540AF0`，一次拿下。**

**顺带还拿到同一条链上的另外三个函数。**

### 通用化

**同时引用两个"有辨识度的常量" ⇒ 命中唯一。**

比如：
- 一对特殊的浮点数（`-10.0f` + `-1.0f`）
- 一个魔法数字数组（本项目的 AI 间隔 `{300, 90, 30, 15, 15}` 全 exe 唯一命中）
- 一个独特的字符串

## ⭐ 方法 2：拿"已验正的同类对象"当尺子

### 适用场景

你有两个结构相同的对象，一个已知正确，另一个待验。

### 实例：`unit_array` 基址错 4 字节

**症状**：读出来的 `count=1`、`elem=160`、`data=0x00FFFFFF` —— 全是垃圾。

**做法**：并排 dump 两个数组的原始内存：

```
firm_array(已验) @0x69FB64: 64 32 01 | [86] | [4] | FFFFFFFF | B4ABA000 …
                                      ↑count  ↑elem

unit_array       @0x69CAB0: ptr C8 64 | 01 | A0 | 04 | FFFFFFFF | 6C8E…
                                        ⇒ 整体错位 4 字节

unit_array       @0x69CAB4: C8 64 01 | [A0=160] | [4] | FFFFFFFF | 6C8E7800 …
                                       ↑count    ↑elem     ↑data ✅
```

**⇒ 一眼看出错位。这个 4 字节坑害了我们三次崩溃。**

### 通用化

**别猜，并排 dump。** 已知正确的那个就是你的标尺。

## ⭐ 方法 3：借鸡生蛋 —— 冒充引擎自己已经在用的调用者

### 适用场景

你要做一件引擎已经在做的事（比如"让一群单位移动"）。

### 做法

**不要自己拼 API 调用**，而是**找到引擎里已经在做这件事的那个函数**，
构造一个假的 `this` 对象喂给它。

### 实例

`Rebel::execute_new_action`（`0x563AC0`）做的就是"收集叛军 → 编组 → 下指令"：

```c
FUN_00469f70(1);                                    // unit_group.zap()
for (i = 1..unit_array.size())
    if (unit_mode == 6 && unit_mode_para == this->rebel_recno)
        FUN_005e6830(i);                            // add_unit(recno)
switch(action_mode) {
    case 2/3: FUN_005e6b50(recno, 2);               // attack
    case 4/5: FUN_005e6ce0(x, y, 0x4C, 2, -1, 0);   // assign
}
```

**⇒ 这段代码在游戏里天天跑、极其稳定。我要做的只是"伪装成叛军"。**

### 为什么这比"自己拼 API"好

| 自己拼 | 借鸡生蛋 |
|---|---|
| 要调 4 个函数 | **只调 1 个** |
| 每个都可能参数错 | 内部调用全由它自己完成 |
| 崩了不知在哪 | 它久经考验 |

## ⭐ 方法 4：从"调用者"反推"被调用者"

### 适用场景

你知道一个函数 A，想找它调用的 B。

### 做法

1. 反编译 A
2. 看 B 被调用时**参数是什么形状**
3. **用参数的语义反推 B 是什么**

### 实例：反查 UnitGroup API 的全局地址

`execute_new_action` 里有 13 个 `call`。挑 4 个像 `UnitGroup` 方法的，
**反查它们入口处 `ECX` 的来源**：

```asm
push [ebp-8]
mov  ecx, 0x0069CAE4     ; ★ 目标对象
call 0x005E6830          ; add_unit
```

**⇒ 直接拿到 `unit_group` 全局地址，不用猜、不用扫。**

## ⭐ 方法 5：从"字段访问模式"认出对象类型

### 实例

`civilian_killed` 有两个调用者：`0x5B6AC0` 和 `0x5E3440`。
我一开始以为 `0x5B6AC0` 是 `Unit::` 侧的（因为它数值小），**错了**。

**看字段访问：**

```
[ecx+0x7e] = 人口
[ecx+0x0b] = 国家
[ecx+0x0c] = 种族
```

**⇒ 那是 `Town::` 的布局**（`otownpop.cpp` 侧）。

**⇒ `0x5E3440` 才是 `Unit::update_being_killed_statistic`。**

## ❌ 无效的方法（别浪费时间）

### 无效 1：猜代码形状 / 精确字节签名

**试过**：

| 假设 | 结果 |
|---|---|
| 连续 6 个击杀计数器自增（`inc dword [reg+disp]` 簇） | **0 命中** |
| `add dword [reg+disp],1` 簇 | **0 命中** |
| 按 `[ecx+5]`/`[ecx+7]` 找 `Skill` 家族 | 15 候选，无一确认 |
| 引用三个数组全局的函数 | **286 候选**（判据太松） |

**⇒ 编译器的优化会让"形状假设"大面积失效。**

### 无效 2：用 `ret N` 收窄（**除非你先数过参数**）

**我犯过的最蠢的一个错**：用 `ret 0x08` 过滤 `civilian_killed`。

**实际它是 3 个栈参数 ⇒ `ret 0x0C`。**

**⇒ 这个筛子亲手把正确答案排除了。**

**⇒ 教训：用 `ret N` 收窄之前，先从源码数一遍参数个数。**

### 无效 3：靠 vtable 相邻槽位推断

**在 Nation 上完全失效**（槽位对不上，而且运行时重定位让"静态 vs 运行时"比较全乱）。

### 无效 4：猜"某个全局地址"

**`firm_array = 0x69FB64` 我们一度怀疑是错的**（因为"运行时读到全 0"）。

**⇒ 那个"全 0"是假阴性** —— 静态 VA 直接按文件偏移读 `.data`，而 `.data` 的 `VirtualSize` 远大于 `SizeOfRawData`
（`0x667C40` vs `0x8400`）⇒ **大部分全局在文件里根本不存在，只有运行时才有。**

**⇒ 铁律：不要把"文件里读到 0"当成"这个地址错了"。**

## 🔒 五条纪律

### 纪律 1：所有 hook 必须带字节指纹校验

```c
static const uint8_t SIG[6] = { 0x55, 0x8B, 0xEC, 0x83, 0xEC, 0x1C };
if (!CheckBytes(VA, SIG, 6)) {
    Log("[X] 字节校验失败 ⇒ 跳过");
    return;
}
```

**⇒ 版本不匹配、地址错了 —— 都不会崩，只会安静地不生效。**

**这条规矩救了我们很多次。**

### 纪律 2：hook 必须用 `__fastcall` 接 `__thiscall`

**目标函数是 `__thiscall`（`this` 在 ECX）⇒ 代理必须声明 `__fastcall`。**

用 `__cdecl` 接会从栈上读垃圾 `self` —— **我们踩过，表现为读出一堆垃圾指针。**

### 纪律 3：一次只改一处，且先改最不重要的

**日期 bug 那次我同时改了月和日两处格式码，两个一起坏、多花一次读档。**

**⇒ 已知能用的那个要留着当对照组。**

### 纪律 4：没有客观锚点就不要动手

**日志里必须内建"能区分两种假说"的量。**

**反例**：我们只打了"已触发守军出巢"，没打"实际新增了多少单位" ⇒ 误判了两轮。

**正例**：改成打 `兵 15->0 监工位 0->16 地图单位 160->160` ⇒ 一行就定案。

### 纪律 5：同一条路连错两次就停

**换方向，别加深。**

**⇒ 本项目在这条纪律上吃过亏**（同一刀被根因推翻 5 次，烧掉估 250~300M token）。

## 🛠 工具链

| 用途 | 工具 |
|---|---|
| 反编译 / 交叉引用 | **Ghidra**（本项目用 REA 接口调用） |
| PE 结构分析 / 字节扫描 | **Python**（`pefile` 或手写 struct 解析） |
| 编译器 | MSVC BuildTools（x86）+ `vcvars32.bat` |
| 资源容器 | 自写 Python 解析器（round-trip 验证） |

**分工原则**：**Python 做分析，C++ 做产物。**

分析脚本便宜、改得快；真正进游戏的东西必须是 C++（性能 + ABI）。

---

## 一句话总结

> **最贵的东西不是"写代码"，是"猜"。**
>
> **浮点常量反查、并排 dump、冒充已有调用者 —— 这三个方法都不需要猜。**
